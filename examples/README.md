# A real evidence bundle

`demo-bundle/` is genuine output from `flight-recorder demo --keep`, committed
so that anyone can look at what this tool produces without installing Go,
building anything, or having a Linux kernel to hand.

Its payload is **synthetic**. The demo command fabricates a memory image,
plants a marker string in it, and runs that through the real pipeline — the
same sealing, signing, encryption and CASE/UCO rendering a live capture uses.
There is no real process memory here, and no private key: `demo-pub.pem` is
the public half of a throwaway keypair that is regenerated on every demo run.

## Verify it yourself

The bundle carries a full cryptographic seal, and you do not need the
decryption key to check it:

```
flight-recorder verify --bundle examples/demo-bundle --key examples/demo-pub.pem
```

```
  [ OK ] manifest file digests        5 file(s)
  [SKIP] payload decryption
  [SKIP] payload sha256
  [SKIP] merkle root
  [SKIP] leaf count
  [ OK ] ecdsa signature
  [ OK ] signer key id
  [ OK ] CASE/UCO structure

SEAL VERIFIED  c5cbd72c-9d1a-48d5-8241-0127a9d020b1
```

That is exactly the position a third-party examiner is in when they are handed
evidence and a public key but not the decryption key. The signature, the
manifest digests and the CASE/UCO document are all proven. The four content
checks are reported as **skipped**, not failed, because they genuinely could
not be run — an examiner should never be shown a red failure on evidence that
is intact.

Hand it the private key instead and all eight checks run, ending in
`VERIFIED`. Change a single byte of `dump.bin.zst.enc` first and it will not.

## Read it without any tooling at all

Four of the six files are plaintext and render in a browser straight from
GitHub:

| File | What it is |
|---|---|
| [`manifest.json`](demo-bundle/manifest.json) | inventory: every file, its SHA-256, its role, whether it is encrypted |
| [`receipt.json`](demo-bundle/receipt.json) | the signed seal: Merkle root, tree parameters, signature, tool identity |
| [`regions.json`](demo-bundle/regions.json) | the memory map, each region's outcome and its offset in the dump |
| [`metadata.jsonld`](demo-bundle/metadata.jsonld) | the CASE/UCO JSON-LD bundle an examiner's toolchain ingests |

This split is deliberate. Triage should not require handing the decryption key
— and therefore every credential in the dump — to whoever is doing the triage.

`dump.bin.zst.enc` is the payload: zstd-compressed, then AES-256-GCM encrypted
in 1 MB frames. `dump.bin.sha256` is the digest of the plaintext, so the
receipt can be checked against the payload once it is decrypted.

## Provenance

Generated by `flight-recorder demo --keep` from a development build, which is
why `receipt.json` records `"tool_version": "0.1.0-dev"` and a
`kernel_version` of `windows-amd64` — the evidence pipeline is pure userspace
and runs anywhere Go runs. Only live acquisition needs a Linux kernel.

Regenerate an equivalent bundle at any time:

```
flight-recorder demo --keep --output ./out
```
